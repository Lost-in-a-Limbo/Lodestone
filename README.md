# Lodestone

A filtered approximate nearest neighbor index in C++20, built from scratch.

**The question this project exists to answer:** what happens to a navigable graph when a metadata filter deletes 99% of its nodes — and can you do anything about it?



---

## The problem

Vector search treats items as points in high-dimensional space and finds neighbors by hopping along a graph of nearest-neighbor shortcuts. HNSW does this extremely well — it's the dominant in-memory index for a reason.

Then you add a `WHERE` clause.

Real queries aren't "find similar documents." They're *"find similar documents **where** `tenant_id = 47` and `status = published`."* The predicate removes most of the graph's nodes, and what survives isn't a smaller navigable graph — it's disconnected islands. Greedy traversal walks into a region where every neighbor fails the filter, has nowhere to go, and stops. The correct answer exists, satisfies the predicate, and is unreachable.

The lower the selectivity — the fraction of the corpus passing the filter — the worse it gets. And low selectivity is the common case in production: one tenant's documents out of ten thousand.

### Why this isn't already solved

| Strategy | How it works | Where it breaks |
|---|---|---|
| **Pre-filter** | Evaluate the predicate, brute-force the survivors | High selectivity — you're scanning hundreds of thousands of vectors |
| **Post-filter** | Search normally, discard non-matching results | Low selectivity — zero survivors in the top-k |
| **In-filter** (ACORN) | Check the predicate during traversal, expand to two-hop neighbors when candidates run out | Below ~1% selectivity — traversal paths fragment and recall collapses |

You could pre-build extra edges guaranteeing connectivity for each filter — roughly what filtered-DiskANN does — but that requires knowing the predicates at index time. Price ranges and date windows make the predicate space effectively infinite.

**The open question:** how do you keep the graph navigable under arbitrary, unknown predicates without paying for it at build time?

## What's in here

```
include/lodestone/
├── distance.hpp      injectable distance interface — scalar, SIMD, or quantized
├── vector_store.hpp  contiguous, 64-byte aligned storage
├── hnsw.hpp          hierarchical navigable small world index
├── filter.hpp        attribute store, predicate evaluation, filter strategies
└── quantizer.hpp     product quantization
```

Everything is written from scratch. `hnswlib` and `faiss` appear only in `bench/` as comparison baselines — never linked into the core.

## Benchmarks

The recall@10-vs-QPS curves against `hnswlib` and `faiss` land with Phase 4 — **including the cases where Lodestone loses and why.** What exists so far is the ground truth everything else will be measured against.

Exact brute force on SIFT1M, single-threaded, machine specs and regeneration commands in [`BENCHMARKS.md`](BENCHMARKS.md):

| Metric | Value |
|---|---|
| Load, 1M × 128 vectors | 0.33 s |
| Peak RSS | 501.6 MiB |
| Brute-force throughput | **32.32 QPS** (median of 3) — 30.9 ms/query |
| Distance kernel | AVX2, **11.1×** hand-written scalar |
| **recall@10** | **1.000000** |

That recall figure has a story attached. Strict id-set comparison against the provided ground truth gives 0.999440, not 1.000 — and the 0.06% gap is not a bug. **SIFT1M contains 14,538 byte-identical duplicate vectors** among its million records, so when a duplicate lands on the k-th boundary, "the 10 nearest neighbours" is not a well-defined *set*: several answers are equally correct, and strict comparison measures whose tie-break convention won rather than whether the search was right. Recall is therefore reported thresholded on the k-th true distance, the ANN-Benchmarks convention.

The order that happened in matters, and it is written down in [`DECISIONS.md`](DECISIONS.md) D17: the shortfall was traced to bit-identical duplicates *before* the metric was changed, not after.

Methodology, fixed for the project:

- Single-threaded queries unless explicitly stated
- 10-second warmup, discarded
- Minimum 10,000 queries per measurement
- Three runs, median reported
- Machine specs captured in every result
- Losses published — where Lodestone is slower, the reason is stated

Every number published here is generated by `bench/` into `results.json`. Nothing is typed by hand.

## Building

Requires CMake 3.21+ (the presets use schema v3), Ninja, a C++20 compiler
(GCC 11 or newer), and a CPU with AVX2 for the fast path.

```bash
git clone https://github.com/lost-in-a-limbo/lodestone
cd lodestone

cmake --preset debug && cmake --build build/debug
ctest --test-dir build/debug --output-on-failure
```

The debug preset enables AddressSanitizer and UndefinedBehaviorSanitizer.

```bash
cmake --preset release && cmake --build build/release
./tools/download_sift.sh          # SIFT10K into data/siftsmall/ (~5 MB)
./tools/download_sift.sh --full   # adds SIFT1M into data/sift/  (~170 MB)
./build/release/bench --all       # writes bench/results/results.json
```

## Design notes

**The distance function is an injectable interface.** Graph code never calls a concrete kernel. This is what lets SIMD (Phase 2) and quantized distances (Phase 5) drop in without touching `hnsw.cpp`.

**Vectors are stored contiguous and 64-byte aligned.** Never `vector<vector<float>>` — the pointer chasing destroys cache locality on the search hot path.

**No exceptions in the search hot path.** Errors return through `std::expected` or an error enum.

Design decisions and their rejected alternatives are logged in [`DECISIONS.md`](DECISIONS.md).

## Why "Lodestone"

A lodestone is a naturally magnetized rock — the original compass. It finds north without a map.

Which is more or less the problem: navigating when most of the map has been closed off.
